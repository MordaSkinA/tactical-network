## 🎯 Зачем это нужно

В GvG-боях у гильдии есть войс-чат, но реально в нём говорит меньшинство игроков. Проблема не в лени: сложно говорить на английском вслух под стрессом боя, когда тебя слышит вся гильдия.

Гипотеза Tacnet простая: если убрать необходимость говорить и печатать текст, заменив это парой кликов, молчавшие раньше игроки начнут делиться интел.

Поэтому интерфейс игрока это не чат, а крупные кнопки: роль врага, критичность, SOS. Прочитать и нажать проще и быстрее, чем формулировать фразу на неродном языке под огнём.

Заодно проект служит portfolio пет-проектом на ASP.NET Core, SignalR и C#, с Blazor в планах на полную версию.

## ⚙️ Как это работает

```
Игрок жмёт кнопку → SignalR Hub → рассылка всем клиентам → Dashboard коммандера / Observer лидеров
```

- **Player** видит текущий приказ своего отряда и жмёт кнопки репортов (роль врага, SOS, статус).
- **Observer** (лидеры отрядов) видит ленту событий по своим людям.
- **Dashboard** (главный коммандер) видит общую ленту по гильдии и рассылает приказы.
- **Admin** управляет ростером (T1–T6, роли Defense / Attack / Flex) через клик-интерфейс, без ручного набора текста.

Единый источник правды это append-only лог `BattleEvent`, поверх которого строятся проекции в памяти. Без Redis, без микросервисов, без event sourcing фреймворков: под задачу такого масштаба (десятки игроков, один бой за раз) это оверинжиниринг.

## 👥 Роли

| Роль | Что видит | Что может |
|---|---|---|
| `Player` | Приказ своего отряда | Репортить роль врага, статус, SOS |
| `Leader` | Наблюдатель за своим отрядом | Смотреть ленту событий отряда |
| `Commander` | Общая лента по гильдии | Рассылать приказы отрядам |
| `Admin` | Всё | Управлять ростером и аккаунтами |

Squad-структура: T1–T6, каждому явно назначена роль Defense / Attack / Flex. Роли врага: TwinBlades / Healer / Tank / Nameless.

## 🚀 Запуск

<details>
<summary><b>Локально</b></summary>

```bash
cd tactical-network
dotnet run
```

Приложение поднимется на `https://localhost:5001` (порт смотрите в выводе консоли). Откройте:

- `/index.html` — вход
- `/menu.html` — роутинг по роли после логина
- `/player.html` — панель игрока
- `/observer.html` — панель наблюдателя (только лидеры)
- `/dashboard.html` — живая лента для коммандера
- `/admin.html` — админ-панель (ростер, аккаунты)

</details>

<details>
<summary><b>Доступ снаружи сети (тест с реальными игроками)</b></summary>

Локальный сервер недоступен снаружи напрямую, поэтому на время теста нужно прокинуть порт через туннель:

```bash
ngrok http https://localhost:5001
# или
cloudflared tunnel --url https://localhost:5001
```

</details>

<details>
<summary><b>Первый вход / сид-аккаунт</b></summary>

При первом запуске, если `accounts.json` пуст, создаётся аккаунт Admin с логином и паролем из `appsettings.json` (`AdminSeedLogin` / `AdminSeedPassword`, по умолчанию `admin` / `changeme`). Смените пароль сразу после первого входа.

</details>

## 📁 Структура проекта

```
tactical-network/
├── Program.cs                  # точка входа, минимальные API, SignalR hub
├── Models/EventModels.cs       # роли, типы приказов, DTO
├── State/
│   ├── InMemoryBattleState.cs  # append-only лог событий + проекции
│   ├── AccountStore.cs         # аккаунты игроков (accounts.json, PBKDF2)
│   ├── SessionStore.cs         # сессии по токену
│   └── RateLimiting.cs         # лимиты на логин и действия в хабе
└── wwwroot/
    ├── index.html               # вход
    ├── menu.html                # роутинг по роли
    ├── player.html               # клик-интерфейс игрока
    ├── observer.html            # панель наблюдателя
    ├── dashboard.html            # панель коммандера
    ├── admin.html                # управление ростером и аккаунтами
    └── js/auth.js                 # общая логика сессии/токена
```

## 🏗️ Архитектура

- ASP.NET Core 8, один проект, один SignalR hub (`/battleHub`), broadcast всем подключённым: на таком масштабе группы и партиции не нужны.
- Аутентификация: логин/пароль (PBKDF2, 100k итераций), токен-сессии, роль и `SquadId` привязаны к сессии на сервере. Раньше при общем админ-ключе клиент мог подделать имя или отряд, теперь физически не может.
- Rate limiting: до 5 попыток логина за 30 сек с одного IP и до 5 действий (репорт/приказ/SOS) за 3 сек с одного подключения.
- Enum'ы гоняются между C# и JS как строки (`JsonStringEnumConverter`), а не числа. Без этого фронт ломался на сравнении ролей со строками.
- Персистентность: ростер лежит в `roster.json`, аккаунты в `accounts.json`. Само состояние боя хранится в памяти и не переживает рестарт сервера, это осознанный компромисс для POC.
- UI-приоритет: клик вместо ввода текста. Старый текстовый формат ростера остался под капотом в свёрнутом блоке "Advanced" для тех, кому проще вставить список.

## ❓ FAQ

<details>
<summary>Почему не Redis / микросервисы / event sourcing фреймворк?</summary>

Потому что масштаб задачи этого не требует: один бой, десятки участников, один процесс. Append-only лог `BattleEvent` в памяти уже даёт нужную историю и проекции. Усложнение архитектуры здесь дало бы только лишние точки отказа.

</details>

<details>
<summary>Почему клики, а не голосовой чат?</summary>

Войс в гильдии уже есть, проблема в том, что им реально пользуется меньшинство. Клик-интерфейс не заменяет войс, а даёт альтернативный канал с более низким порогом входа для тех, кому сложно говорить вслух на английском под стрессом боя.

</details>

<details>
<summary>Данные боя переживают перезапуск сервера?</summary>

Нет, состояние боя хранится в памяти и намеренно не персистится (POC). Персистентны только ростер (`roster.json`) и аккаунты (`accounts.json`).

</details>
